训练一个真正能在终端里持续工作的 Agent，难点不只是让模型多执行几条命令，而是为它准备足够多的**长程、可执行、可验证**的任务和交互轨迹。

这类数据远比普通的指令问答昂贵。一个 Terminal 任务至少要同时保证：用户指令说得公平，初始环境可以复现，任务确实有解，验证器能够判断结果，而且这几部分不能互相矛盾。只让大模型生成一段更长的任务描述很容易；让它生成一个从初始状态开始能够跑通、不会泄露答案、又能自动判分的完整任务包，则是另一回事。

《[Recursive Synthesis for Long-Horizon Terminal Tasks](https://arxiv.org/abs/2608.05466)》提出的 RST（Recursive Synthetic Terminal Tasks）把这个问题变成了一条递归运行的“任务工厂”：从少量已经验证过的任务出发，先扩展参考解法（oracle solution），再同步重写验证器（verifier）、公开指令（public instruction）和环境；只有在全新沙箱中重新跑通的任务，才会进入下一轮并用于采集训练轨迹。

最终，RST 从 639 个种子任务出发，经过 15 轮递归合成得到 37,484 个经过验证的 Terminal 任务，平均每个通过任务的生成成本约为 0.05 美元。更重要的是，它展示了一套可复用的工程方法：**扩大高质量轨迹的关键，不是先批量生成轨迹，而是先批量制造可靠的、难度可增长的轨迹发生器。**

## 先分清两个数据单位：Task 不等于 Trajectory

理解 RST 前，首先要区分“任务”和“轨迹”。

一个 **Task（任务）** 是可重复运行的完整环境，包含：

```text
task/
├── instruction.md          # Agent 可见的公开任务说明
├── task.toml               # 运行时配置与资源信息
├── environment/Dockerfile  # 初始环境和工作区
├── solution/solve.sh       # Agent 不可见的参考解法 / Oracle
├── tests/test.sh           # 私有验证入口
└── tests/test_state.py     # 私有状态与结果检查
```

一个 **Trajectory（轨迹）** 则是某个 Agent 在这个任务上的一次实际交互记录：模型观察了什么、执行了哪些命令、终端返回了什么、模型如何根据反馈继续行动，以及最终得到了多少验证器奖励。

同一个任务可以被不同模型、不同 checkpoint 或不同采样随机性重复运行，从而产生多条轨迹。因此，RST 的扩展逻辑实际上有两层：

```text
少量已验证任务
    ↓ 递归改写与验证
大规模可复用任务池
    ↓ 多模型、多次 rollout
大规模交互轨迹
    ↓ 验证器筛选或提供稠密奖励
SFT 成功轨迹 + RL 训练样本
```

![RST 递归任务合成与下游训练的整体流程](/assets/blog/2026-08-31-recursive-synthesis-for-long-horizon-terminal-tasks/figure-2-rst-overview.png)

*图 1：RST 的整体数据闭环。通过验证的任务一方面被重新选为下一轮种子，另一方面直接组成 verifier-based RL 的任务池；Agent 在这些任务上的成功 rollout 则成为 SFT 轨迹。图片来源：原论文 Figure 2。*

这一区分非常重要。直接让模型“编一条成功轨迹”，很难确认轨迹中的命令是否真的执行过，也难以知道它是否只是在文本层面伪造了成功。RST 先建立可执行任务，再让 Agent 在隔离环境中真实行动，轨迹质量最终由环境状态和私有验证器决定，而不是由生成模型自己声称“已完成”。

## 一个合成任务必须满足两种有效性

RST 不把“参考脚本运行成功”当作唯一准入条件，而是同时要求两种有效性。

### 1. Oracle validity：任务确实有解

在一个全新的沙箱中，从规定的初始状态启动环境，执行 `solution/solve.sh`，然后运行私有验证器。只有验证器返回满分，并且执行过程中没有异常，任务才具有 Oracle validity。

这相当于让每个任务都携带一份**可执行的可解性证明**。它排除了 Dockerfile 构建失败、依赖缺失、路径错误、参考解法漏产物、验证器与解法不一致等问题。

### 2. Contract validity：Agent 面对的是公平任务

验证器中每一项会影响奖励的语义要求，都必须满足以下二者之一：

- 已经明确写在公开指令里；
- 可以通过工作区内的 README、配置、fixture、源码、日志或正常命令输出发现。

私有测试不能凭空增加 Agent 永远不可能知道的要求。与此同时，公开指令也不能把私有测试、完整命令序列和逐字段验收规则全盘泄露给 Agent，否则任务会退化成照抄验收表。

因此，RST 的质量标准不是单纯的“能跑通”，而是：

> 任务有解；判分有依据；成功条件对 Agent 公平；但具体解法仍需通过终端探索得到。

## RST 的主循环：从一个验证过的任务，长出更难的任务

每一轮递归合成可以概括为四个阶段：

1. 从上一轮通过的任务中选择种子，并确定适合它的改写方向；
2. 先扩展参考解法，再对齐验证器、指令和环境；
3. 经过本地规则检查和全新沙箱中的 Oracle 验证；
4. 将通过的任务加入训练任务池，并从中选择一个多样化子集作为下一轮种子。

![RST 单轮递归合成的任务改写与验证流程](/assets/blog/2026-08-31-recursive-synthesis-for-long-horizon-terminal-tasks/figure-3-recursive-round.png)

*图 2：单轮递归合成的完整流程。系统保留种子任务的文件结构，通过增加执行步骤、状态依赖和更严格的语义检查来提高难度；本地检查过滤表面或畸形改写，沙箱 Oracle 验证任务确实可解，可恢复失败根据日志有限修复。最终仅从通过任务中选择多样化子集进入下一轮。图片来源：原论文 Figure 3。*

这里真正决定质量的是下面这些实现细节。

为了让后面的步骤更直观，可以先设想一个贯穿全文的小例子：种子任务要求读取 `/app/data/` 中的 CSV 文件并生成汇总报告 `report.json`，工作区的 README 描述了字段含义。RST 不会简单地把指令改成“处理更多文件”，而可能在保留汇总目标的基础上，增加输入清单核对、异常行处理、checksum 和 provenance 记录。于是，Agent 必须先发现本地规则，再处理数据、校验计数，最后生成彼此一致的报告与证据文件。

## 第一步：不要随机“加难”，先判断种子提供了哪些可供性（affordance）

不同任务适合增加的难度不同。一个带有 `package.json` 和构建脚本的任务，适合加入依赖版本、lockfile、构建产物或 CLI 行为约束；一个包含数据库和迁移文件的任务，可能适合加入状态迁移、备份回滚或幂等性；一个拥有日志和服务进程的任务，则适合加入故障诊断、端口检查或生命周期管理。

RST 为此定义了 40 个改写算子（rewrite operators），并将它们组织为五个改写算子族（rewrite families），对应五类可执行难度来源：

| 难度来源     | 典型改写                                                                      |
| -------- | ------------------------------------------------------------------------- |
| 环境与运行时   | 依赖版本对齐、工作目录与路径修复、权限、环境变量、工具链、容器构建、服务生命周期、资源清理                             |
| 构建、测试与执行 | 编译打包、测试失败修复、集成流程、CLI 参数行为、静态检查、运行时调试、构建产物、性能 smoke test                   |
| 数据、产物与报告 | 格式转换、Schema 校验、汇总报告、清单核对、压缩归档、去重规范化、校验和与溯源、二进制元数据                         |
| 配置与持久状态  | 配置和数据一致性、manifest/lockfile 对齐、状态迁移、缓存与索引重建、数据库初始化、模板一致性、feature flag、备份回滚 |
| 诊断、审计与取证 | 日志诊断、事件关联、验证失败解释、权限审计、数据异常调查、进程与端点检查、Git 历史分析、证据包生成                       |

这些类别不是按“软件工程、数据分析、安全”等应用领域划分，而是按**任务可以在哪里增加可执行复杂度**划分。同一个数据处理任务可以增加构建复杂度，也可以增加状态迁移或故障诊断复杂度。这样的分类更适合指导自动改写。

对每个种子，系统会进行本地可供性扫描（local affordance scan）：扫描公开指令、参考解法、验证器、配置和环境文件的有界表示，寻找 package manifest、结构化数据、构建脚本、CLI、归档文件、数据库、日志、权限、服务和版本约束等信号。然后综合三类信息选择算子：

- 算子与当前种子的局部兼容性；
- 当前批次中不同算子、不同 family 的平衡；
- 对已经被频繁选择的算子施加逆频率惩罚。

选择器会记录一个首选算子、最多五个可行备选，以及明确不适用于该种子的算子。随后再进行模型排序（affordance ranking），判断首选算子是否自然、安全、具有足够的本地证据。模型可以改选备选项，但不能绕过前面的局部扫描，凭空选择一个已被排除的算子。

以前面的 CSV 任务为例，工作区已经存在结构化数据、报告格式和输入文件，因此 `checksum_hash_provenance` 或 `artifact_inventory_reconciliation` 是自然的改写算子；如果任务中没有服务、端口或进程，却硬套 `service_process_lifecycle`，就只能凭空引入额外环境，改写既不自然也更容易失败。**算子不是给任务贴的主题标签，而是规定“通过什么可执行机制让任务变难”。**

这套“规则先缩小空间、模型再做语义判断”的组合兼顾了吞吐量和自然度，也避免所有任务都被改写成少数最容易生成的模式。

## 第二步：先写任务变换契约（task transformation contract），再允许模型改文件

选出算子后，RST 不立即让模型修改任务，而是先生成一份结构化的任务变换契约（task transformation contract）。它是所有后续文件之间的共同真源（source of truth），至少定义：

- 原任务中必须保留的核心工作流；
- 本轮新增的、用户可感知的 Terminal-native 要求；
- `inspect → derive → execute → validate → finalize` 的任务链；
- 每个阶段对应的证据、过程产物和最终产物；
- 验证器应该检查的语义结果；
- 如何拒绝空文件、过期产物、硬编码答案和只针对验证器的投机解法；
- 哪些信息必须出现在公开指令里，哪些可以留在工作区供 Agent 探索。

契约要求至少提供四类可区分的奖励检查（reward checks）：

1. **证据发现**：Agent 所需的本地证据确实存在且可被找到；
2. **中间状态有效**：过程产物存在、可解析且非空；
3. **最终语义正确**：结果在内容或系统状态上真正满足目标；
4. **反捷径**：拒绝 placeholder、陈旧结果、硬编码和仅迎合验证器的输出。

契约会拒绝三种常见的伪难度：只做表面重构、只加强测试却不增加用户可见工作、以及把关键要求藏在私有测试里。它也限制引入大型依赖、联网服务和无界后台任务，因为这些变化会显著提高基础设施成本和不稳定性。

对应到 CSV 示例，一份简化的契约可以是：

```text
preserved_workflow: 读取 CSV 并生成 report.json
new_requirement:     核对输入清单，并生成可验证的 checksum/provenance
task_chain:          inspect → derive → execute → validate → finalize
expected_artifacts:  report.json + manifest.json
reward_checks:       找到本地规则 / 中间结果可解析 / 汇总语义正确 / 拒绝硬编码旧报告
```

这与直接提示模型“把任务改难一点”不同：后者可能只把指令写长，或者只在私有测试里增加断言；契约则要求新增目标、执行步骤、可观察产物和判分条件彼此对应。

这一步的价值在于，把一句含糊的“让任务更难”变成可以逐文件实现、逐阶段检查的工程规格。

## 第三步：解法优先（solution-first），先扩展真实执行路径

RST 最关键的设计选择是 **grow solution, then align**：先扩展 `solution/solve.sh`，然后让其他组件围绕新的执行路径对齐。

新的参考解法必须从原始初始状态开始，保留种子任务的核心行为，并按顺序完成契约中的完整任务链。它通常会加入以下操作：

- 先检查输入、配置、源码、日志或当前系统状态；
- 从本地证据推导参数、路径、Schema 或预期状态；
- 调用真实 CLI、编译器、数据库或项目脚本；
- 生成可观察的中间产物；
- 对中间结果做有界校验后，再写入最终产物；
- 在合理范围内保持确定性、幂等性和重复执行安全。

参考解法不能硬编码只存在于验证器中的常量，不能用一个 `echo` 伪装完整工作流，也不能删除原任务逻辑来迎合新的测试。

为什么必须 solution-first？因为长程难度应该来自更多真实的状态依赖与执行工作，而不是来自更长、更绕的自然语言。先建立一条真实可执行的成功路径，验证器才有明确对象，指令也才能围绕真实目标进行压缩表达。

仍以 CSV 任务为例，“指令优先”的改写可能先写出一串听起来复杂的要求，之后才发现环境里没有输入清单或 checksum 工具；solution-first 则先确认参考脚本能从 README 和现有 CSV 推导文件集合，实际生成 `report.json` 与 `manifest.json`，再让验证器和指令描述同一条已跑通的路径。

## 第四步：围绕执行路径，对齐另外五个文件

任务构建按文件作用域分阶段完成，生成阶段只能修改六个白名单文件，越界写入直接拒绝。

### 4.1 从契约生成验证器（verifier），而不是照抄解法命令

`tests/test_state.py` 和 `tests/test.sh` 检查的是用户可见结果、重要中间状态以及原任务必须保留的行为，而不是强制 Agent 复现 `solve.sh` 的逐条命令。

好的验证器应该检查语义，而非实现细节。例如，检查 manifest 与真实产物是否一致，比检查 Agent 是否执行过某条固定的 `jq` 命令更稳健；检查归档内容、checksum 和来源关系，比检查一个文件是否存在更难被占位符欺骗。

例如，CSV 任务的验证器应该重新计算行数与 checksum，确认 `report.json`、`manifest.json` 和真实输入一致；它不应该要求 Agent 必须调用 `sha256sum`，因为用 Python 计算相同 SHA-256 也是合法解法。前者验证“结果是否正确”，后者只是模仿参考脚本的命令顺序。

同时，验证器需要提供足够明确的失败信息，用于定位缺失产物、错误格式和不一致状态，但错误信息不能泄露完整解法。

### 4.2 将公开指令（public instruction）控制为“公平目标”，而不是验收清单

公开指令一般保持为 1 到 3 个短段落，目标长度约 80 到 130 个英文词。它应包含：

- 用户真正想完成的目标；
- 一到两个公平的起点，例如工作目录或本地说明文件；
- 主要交付物或完成信号；
- 无法从工作区发现的硬性常量。

它不应包含私有测试路径、完整文件清单、逐字段 Schema、Oracle 命令序列或“反复运行测试直到通过”式的答案导向。能够从 README、配置、fixture 或日志中发现的细节，应该留给 Agent 自己探索。

这种边界看似只是写作风格，实际上直接影响轨迹质量：指令过细会让 Agent 绕过探索和推理，产生大量短而机械的 reward-hacking 轨迹；指令过少则会制造不公平的零奖励样本。

例如，较合适的公开指令是：“按照 `/app/README.md` 中的数据约定处理输入，生成汇总报告及其完整性清单。”不合适的写法则会直接列出每个字段、checksum 值、所有中间路径和私有断言。前者给出公平起点和交付目标，细节仍需探索；后者实际上把验证器变成了答案模板。

### 4.3 只在必要时调整环境和元数据

如果新工作流需要少量本地依赖、fixture、配置或资源设置，系统才修改 `environment/Dockerfile` 或 `task.toml`。默认选择是不改。

环境修改必须保持自包含：不依赖运行时互联网、密钥或外部服务；Docker `COPY` 的源必须存在；被指令隐去的细节必须能在容器内的本地文件或命令输出中发现；资源和 timeout 也不能为了“显得更难”而随意膨胀。

### 4.4 做一次跨文件一致性修复（consistency repair）

初次生成后，系统会枚举并比对四张清单：

1. 验证器要求存在或满足条件的文件与状态；
2. 参考解法实际创建或修改的文件与状态；
3. 契约承诺的证据、中间产物和最终产物；
4. 每项 reward check 对应的验证器子检查。

然后按顺序“心智执行”参考解法，检查环境是否真的提供了所需 fixture，指令所指向的 README、配置或日志是否确实存在。发现不一致时，优先修复解法、环境或公开证据，而不是削弱验证器。

## 第五步：用廉价静态门控，挡住明显坏样本

沙箱构建和执行是昂贵步骤，所以 RST 在此之前放置了两道确定性门控。

### 生成质量门控（generation-quality gate）

它要求改写必须具有实质性。在论文当前实现中：

- 至少三个任务文件发生变化；
- 参考解法至少有八行变化；
- 验证器至少有十二行变化。

这些阈值不是难度指标，只是用来排除表面改写和“只改测试”的伪任务。

同一道门还会拒绝泄露私有测试路径、像逐步命令教程、罗列过多实现细节、超过 180 词，或者长度超过父任务 1.6 倍的公开指令。边界情况可以保留 warning，但严重违规直接淘汰。

### 静态预检门控（static-preflight gate）

它在不启动完整沙箱的情况下检查：

- 必需文件和 metadata 是否完整；
- Dockerfile 是否可解释，`COPY` 源是否存在；
- 验证器需要的产物是否由解法生成或由环境提供；
- 契约声称可发现的证据是否真的存在；
- 关键路径、配置和环境是否互相一致。

这样可以把 token 生成问题、静态结构问题与后面的动态执行问题分开记录，也避免把显然构建不了的任务送进 Daytona。

## 第六步：执行沙箱 Oracle 验证（sandbox oracle validation），并只做有限反馈修复（feedback repair）

通过静态检查的候选任务会交给 Harbor，在全新的 Daytona 沙箱中执行一次参考解法，再运行私有验证器。只有同时满足以下条件才算 `oracle-passed`：

- 验证器奖励为 1；
- 整次 trial 没有执行异常。

其余结果被分类为零奖励、构建失败、运行时错误、超时、输出过量或未知错误。对于可恢复错误，修复模型会收到 transformation contract、截断后的构建日志、执行日志、验证结果和失败元数据。它必须先判断具体根因，然后只能在六个白名单文件内做最小修复。

修复不能通过删除语义检查、取消反捷径规则或把私有要求抄进公开指令来“刷通过”。修复后的任务必须重新经过 static preflight，并在一个新的沙箱中重新验证。论文配置最多允许两轮反馈修复；仍然失败的候选直接丢弃。

例如，若动态日志显示 `manifest.json` 缺少一个由参考解法漏写的输入项，修复应补齐 `solve.sh` 的清单生成逻辑；如果 Docker build 报告缺少 `COPY` 源，则修复 Dockerfile 或任务配置。系统不能为了通过而删除该项验证，也不能把预期 checksum 从私有失败日志抄进公开指令。

“有限修复”是控制质量的关键。如果允许模型无限修改直到测试通过，任务可能逐步偏离原始契约，验证器也可能被越改越弱。两轮上限迫使系统保留原始变换意图，也使生成成本和失败统计保持可解释。

最终清单（manifest）只收录通过最后一次验证的任务，并保留父任务、轮次、生成批次（cohort）、改写算子、修复次数、初始与最终结果以及文件路径等来源信息（provenance）。

## 第七步：用多样性上限（diversity caps）同时控制难度、稳定性和多样性

如果每轮简单地从通过任务中随机抽样，递归数据很容易出现三种坍缩：

- 少数高产父任务拥有大量后代，数据看似很多，实际血缘高度重复；
- 少数通用算子不断占据任务池，执行模式越来越单一；
- 过难或基础设施不稳定的任务反复成为种子，导致下一轮通过率下降。

RST 会读取上一轮所有 `final_manifest.json` 中的通过记录，按真实任务路径去重，并保留轮次（round）、循环（loop）、生成批次（cohort）、算子族（family）、算子（operator）、修复记录（repair）和原始父任务等元数据，形成下一轮的 `pool_manifest.jsonl`。

每个候选种子的评分综合考虑：

- 静态风险与环境成本；
- 改写 family/operator 与验证历史；
- 构建 timeout 和资源密集特征；
- 是否需要过修复，以及修复次数；
- 若已有 rollout 统计，则考虑成功率、基础设施错误率和交互长度。

选择器偏好**非零但不平凡的成功率**：通过率过高可能说明任务太容易；几乎没人成功或基础设施错误很多，则可能是不稳定任务。需要一次修复但最终完整通过的任务仍可使用，反复修复的任务会受到稳定性惩罚。

标准配置的目标是每轮选出 1,000 个种子，并设置以下上限：

- 同一原始父任务最多 4 个后代；
- 同一 category 最多 160 个任务；
- 同一 rewrite family 最多 320 个任务；
- 同一 source cohort 最多 280 个任务。

如果无法凑够目标数量，系统会按预先定义的顺序逐步放宽约束，并记录每次使用的 cap，而不是在最后悄悄取消多样性限制。

递归血缘（lineage）本身也被当作质量数据维护。过长任务名会压缩到最多 96 个字符，同时保留 bootstrap 父任务标识并附加稳定 hash。对至少包含 20 条记录的 manifest，系统要求至少 80% 的记录能够恢复 bootstrap 血缘；这一检查在选择前、选择后和物化后各做一次，失败则直接终止本轮。否则，同父任务上限和血缘多样性分析都会失效。

## 从验证任务池到高质量轨迹池

经过上述流程，每个通过任务（accepted task）都是一个可重复执行轨迹采样（rollout）的“轨迹发生器”。论文使用 Harbor 作为统一执行与记录框架，Terminus-2 负责把公开指令和初始化工作区交给 Agent，Daytona 提供隔离沙箱。Agent 可以读取文件、运行命令并修改工作区，但无法访问 `solution/solve.sh` 和私有验证器。交互结束后，系统在最终工作区上运行验证器。

任务池随后以两种方式服务训练：

### SFT：只保留真实成功的 rollout

在合成任务上让 Qwen3.5 自行 rollout，通过拒绝采样（rejection sampling）保留成功轨迹。这里的“成功”不是模型文本中的自我判断，而是私有验证器对最终环境状态的判定。论文共报告了 327,189 条 Agent 交互轨迹；成功轨迹被整理成 message 与 metadata 记录，用于监督微调。

这种方式的优势是每条 SFT 样本都来自真实终端执行，并且有可执行结果背书。代价是困难任务的成功样本率较低，因此需要重复 rollout、合理的采样温度、交互长度上限和稳定的并发沙箱基础设施。

### RL：任务本身直接提供可执行奖励

37,484 个合成任务组成基于验证器的强化学习（verifier-based RL）任务池。每个 batch 混合不同轮次和难度，内置验证器不仅能判断最终成功，还可以通过多个子检查提供部分奖励（partial credit）。这样，未完全成功的长轨迹也能包含“发现证据、生成中间产物、完成部分状态转换”等学习信号。

因此，RST 对“扩大轨迹规模”的贡献不只是增加成功 SFT 样本。它同时扩大了：

- 可反复采样的环境数量；
- 任务难度和执行模式的覆盖；
- 成功轨迹的来源；
- 失败轨迹中可用于 RL 的稠密反馈。

## RST 与几种相近做法有什么不同

下面是方法层面的简化对照，目的是说明各自扩展的数据单位不同，并不意味着所有相关工作都严格属于某一行。

| 做法 | 主要生成什么 | 质量依据 | 主要缺口 |
| --- | --- | --- | --- |
| 只做指令演化（instruction evolution） | 更长或更难的任务文本 | 文本规则或模型评分 | 不保证环境、解法和验收条件同步可执行 |
| 直接合成轨迹（direct trajectory synthesis） | 看似成功的命令与观察序列 | 模型自评或文本一致性 | 命令可能没有真实执行，最终状态难以证明 |
| 一次性生成解法与测试 | 单轮可验证任务 | 参考解法是否通过测试 | 可以得到可执行样本，但没有解决递归复用时的难度、多样性和血缘控制 |
| RST | 指令、环境、参考解法、验证器和配置组成的完整任务包 | Oracle validity + contract validity | 工程链路更重，但任务可以递归复用，并持续产生 SFT/RL 轨迹 |

用 CSV 示例来看：只做指令演化可能只是增加一句“同时生成 provenance”；直接合成轨迹可能写出一段并未真实执行的 `sha256sum` 日志；一次性任务生成可以证明当前版本可解；RST 则进一步要求这个版本通过端到端验证、保留来源信息，并在多样性约束下决定它是否适合成为下一轮种子。

## 为什么这套方法能够高效扩展

从工程角度看，RST 的效率来自几层漏斗协同工作：

```text
规则扫描缩小改写空间
        ↓
结构化契约减少跨文件歧义
        ↓
按文件分阶段生成，降低一次性生成难度
        ↓
本地静态门控提前过滤廉价错误
        ↓
沙箱只验证更可能成功的候选
        ↓
失败日志驱动最多两轮定向修复
        ↓
通过任务进入递归池并反复产生轨迹
```

论文的实验主要用于证明这条生产线没有随着递归而失控：15 轮中，每 1,000 次种子尝试得到约 498.2 到 572.2 个通过任务；候选通过率稳定在 74.5% 到 81.5% 之间。与此同时，从 R1 到 R15，参考解法的中位长度从 67 行增长到 374 行，执行命令中位数从 40 增长到 244，而指令长度只增长约 1.4 倍。

也就是说，任务变难主要来自真实执行链和状态依赖的增长，而不是提示词注水。DeepSeek-V4-Pro 的 pass@4 从 R1 的 90% 降到 R15 的 2.5%，但合成产率和验证成功率没有随之崩溃。这正是递归数据工厂需要的性质：**难度持续增长，生产过程仍然稳定。**

## 一个具体例子：JSON-diff 任务如何长成长期工作流

论文跟踪了一条从种子到 R15 的完整血缘。最初的任务只要求运行 `gendiff` CLI，对固定的 JSON fixture 生成差异报告。后续轮次没有换掉这个核心目标，而是逐步加入：

- 用 `tasks.json` 描述任务矩阵；
- 识别并修复无效配置；
- 添加新的 regression case；
- 保持 fixture、预期计数、生成报告和测试之间一致；
- 根据失败证据诊断问题；
- 更新 release note 并完成项目级验证。

到 R15，Agent 需要检查工作区证据、修复配置和 fixture 数据、重新生成全部报告、核对实际与预期计数，并完成项目验证。参考解法由最初的 10 行非空 shell 代码增长到 347 行，但任务仍然属于同一个 domain，核心目标也仍可识别。

这个例子揭示了“长期任务”的一个更实用定义：不是把多个无关小任务拼在一起，而是在同一目标下增加更多前后依赖的状态转换，让后一步必须建立在前一步的真实结果上。

## 如果要复现这套生产线，最值得保留的检查表

RST 的具体模型、Harbor 或 Daytona 都可以替换，但以下原则最好不要省略。

### 任务生成

- 从已经通过端到端验证的任务开始，不从纯文本指令开始。
- 用环境 affordance 决定难度增长方向，不生硬套用随机改写。
- 先生成结构化变换契约，再修改任务文件。
- 先扩展成功执行路径，再生成验证器和公开指令。
- 每轮只增加一个主要难度机制，保留父任务核心工作流。

### 质量控制

- 同时要求 Oracle validity 和 contract validity。
- 验证语义结果和状态变化，不绑定唯一命令顺序。
- 为证据、中间状态、最终语义和反捷径分别设置检查。
- 所有 reward-relevant 条件必须公开或可从工作区发现。
- 在昂贵的沙箱执行前做跨文件静态检查。
- 修复必须有次数上限、文件白名单和明确失败分类。
- 任何修复都不能以削弱验证器为代价。

### 递归扩展

- 在 manifest 中保留 round、parent、cohort、operator 和 repair provenance。
- 同时约束父任务、领域、算子 family 和生成 cohort。
- 优先选择有挑战但并非近乎不可解的任务。
- 把基础设施失败与 Agent 能力失败分开统计。
- 在选择、复制和生成前后持续检查血缘是否可恢复。

### 轨迹采集

- 每次 rollout 都从干净、隔离、可复现的环境开始。
- Agent 永远不能访问参考解法和私有验证器。
- SFT 轨迹由可执行验证器筛选，不依赖模型自评。
- 保留失败类型、partial reward、轮次和任务 provenance。
- 对困难任务增加 rollout 次数，而不是降低成功标准。
- 将任务数量、rollout 数量、成功轨迹数量分开报告。

## 总结

RST 最值得借鉴的不是“递归调用大模型”本身，而是它对递归生成施加的完整约束：

> 用已验证任务作为种子，以真实执行路径作为难度载体，以结构化契约协调跨文件生成，以静态规则和沙箱 Oracle 控制质量，以有限修复回收可恢复样本，再用 provenance 和多样性上限防止递归坍缩。

经过验证的任务既可以反复 rollout，筛选出高质量 SFT 轨迹，也可以直接通过私有验证器提供 RL 奖励。于是，数据扩展的基本单位从昂贵的一次性人工轨迹，变成了一个能够重复生成交互、持续提供反馈的可执行环境。

这也许是这篇论文对 Terminal Agent 数据生产最重要的启示：**先规模化生产可信的任务与验证机制，轨迹规模才会随之增长；如果环境、契约和验证器不可靠，生成再多轨迹也只是更快地扩大噪声。**
